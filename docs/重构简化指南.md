
### 一、项目目标与原则

- **核心功能**：构建一个多用户SaaS平台，用户可使用不同的AI服务商、配置不同费率、访问不同模型。
- **设计原则**：
    - **零依赖部署**：最终交付物为单个二进制文件 + SQLite  数据库 + GORM，无需PostgreSQL、Redis或Docker。
    - **插件化架构**：新增一个AI服务商或支付渠道，只需添加1个文件并注册，无需修改核心代码。
    - **适度简化**：保留运营监控等必要功能，砍掉过度设计。
- **量化目标**：数据表从75个减少到15个，内存占用从约220MB降至约40MB，部署步骤从10+步简化到1步。

### 二、功能取舍

- **保留的核心功能**：用户/密钥/账户管理（合并为4个表）、优惠码与兑换码（营销与充值）、公告（通知）、错误日志（排障）、系统指标（监控）。
- **删除的非核心功能**：分组系统（权限改为直接配给用户）、联盟返利、用户属性（改用JSON字段）、订阅计划（改用用户字段）、聚合表（改为实时查询+缓存）、告警、定时测试、渠道监控（合并到指标表）。

### 三、数据库设计核心约定

- **金额单位**：所有金额统一使用整数（INTEGER）存储，单位为“万分之一元”，以避免浮点数精度问题。
- **时间格式**：所有时间字段统一使用整数（INTEGER）存储毫秒级Unix时间戳，以提升排序和范围查询性能。
- **凭据安全**：AI服务商账户的凭据（`credentials`）使用AES-256-GCM加密后存储，加密密钥从配置文件读取。
- **删除策略**：采用物理删除（`DELETE`），不使用逻辑删除（`deleted_at`），并通过外键`ON DELETE CASCADE`自动清理关联数据，防止数据库文件膨胀。
- **ID设计**：所有自增ID从10000开始，避免数据看起来像测试数据。
- **模型价格管理**：模型价格不作为静态配置文件，而是存入`model_prices`表，管理员可通过前端管理页面实时增删改查，无需重启服务。启动时价格会加载到内存缓存，前端修改后通过事件实时刷新。
- **运营简化**：
    - **优惠码**：使用记录以JSON格式内嵌在优惠码表中，仅保留最近N条。
    - **公告**：阅读数使用计数器，不追踪单个用户的已读状态。
    - **OAuth会话**：OAuth流程中产生的临时数据单独存放，登录完成后立即删除，过期会话由定时任务自动清理。

### 四、订阅转API核心指导（本项目最核心功能）

- **一句话总结**：管理员通过OAuth登录添加其AI服务商（如ChatGPT Plus）的订阅账户 → 系统自动管理这些账户的Token生命周期 → 普通用户使用平台发放的API Key即可透明地调用背后这些订阅账户的AI模型。
- **支持的账户认证类型**：共6种，包括完整OAuth、仅推理scope的OAuth、静态API Key、上游透传、AWS Bedrock及Google Service Account。`oauth`类型是核心，需要系统自动刷新Token。
- **OAuth登录与Token生命周期管理（以Claude为例）**：
    1.  **生成授权URL**：后端生成PKCE安全参数和防CSRF的state，构造AI服务商的授权链接。
    2.  **管理员授权**：管理员在浏览器完成登录授权，服务商回调携带授权码。
    3.  **交换Token**：后端使用授权码和PKCE参数向服务商换取`access_token`和`refresh_token`。
    4.  **安全存储**：将获取的Token等凭据加密后存入`accounts`表。
- **Token刷新机制（三层保护）**：
    1.  **请求路径刷新**：每次API请求时，检查Token是否即将过期（3分钟窗口），若是则触发刷新。刷新失败时，对不同平台有不同的降级策略（如Claude/OpenAI会降级使用旧Token以保证服务不中断）。
    2.  **后台定时刷新**：一个后台服务定时扫描所有活跃的OAuth账户，提前刷新即将过期的Token，并带有重试机制。
    3.  **内存缓存层**：获取到的Token会缓存在内存中，避免每次请求都查询数据库和检查过期。
- **统一刷新API**：封装了通用的刷新逻辑，包括进程内互斥锁、数据库重读、二次检查（防止并发刷新）等，确保在单实例部署下的Token刷新安全性。
- **请求转发完整链路**：用户API Key认证 → 账户选择（根据负载、优先级、并发数调度） → 获取有效AccessToken → 向上游AI服务商转发请求 → 流式返回响应并异步记录用量和扣费。

### 五、Provider插件化架构指导

- **设计原则**：将AI服务商的功能抽象为多个小接口（如端点管理、请求转换、错误处理等），Provider按需组合实现，而非实现一个庞大的完整接口。
- **核心接口**：`EndpointProvider`（端点映射）、`RequestProvider`（请求头和体转换）、`StreamProvider`（流事件处理）、`ErrorProvider`（错误解析与识别）、`TokenProvider`（Token获取与刷新）。
- **注册与使用**：在程序入口（`main`函数）显式注册各个Provider，而非使用自动注册。通过`Registry`获取Provider后，使用类型断言安全地获取其支持的特定能力接口。
- **新增Provider步骤**：只需在`provider`目录下创建一个新包，实现所需的接口，然后在`main`函数中注册即可。

### 六、支付模块插件化指导

- **设计理念**：支付渠道与AI服务商采用完全一致的插件化架构。
- **核心接口**：`CreateOrderer`（创建支付订单）、`CallbackHandler`（处理支付回调）、`Refunder`（执行退款）。
- **订单状态简化**：从11种状态简化为6种核心状态：`PENDING`、`PAID`、`EXPIRED`、`CANCELLED`、`REFUNDING`、`REFUNDED`。
- **支付/审计表简化**：订单表和审计日志表合并为2个核心表。
- **退款流程**：退款前检查用户余额是否足够扣除，退款流程（更新状态、调用渠道退款、扣减余额、记录审计）在数据库事务中完成，保证一致性。
- **新增支付渠道步骤**：只需在`payment`目录下创建一个新包，实现所需接口，然后在`main`函数中注册并添加配置即可。

### 七、部署与项目结构

- **构建**：使用交叉编译生成多平台（Linux/Windows/macOS，amd64/arm64）的单个可执行文件。前端代码会构建并嵌入到后端二进制文件中。
- **运行**：直接运行二进制文件，通过命令行参数或配置文件指定端口、数据库路径等。
- **数据库**：使用SQLite，`WAL`模式开启以支持读写并发。部署时备份仅需复制单个`.db`文件。
- **项目结构**：后端代码位于`server`，前端代码位于`web`。后端内部按`config`、`provider`、`payment`、`handler`、`service`、`repository`等职责分包，结构清晰。
